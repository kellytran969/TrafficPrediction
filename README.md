# Traffic Prediction

A real-time traffic forecasting system: synthetic sensor streams from road
sensors across major U.S. metros flow through a streaming pipeline into
Postgres, get cleaned and aggregated by a batch ETL, train ML models, and are
served as live predictions through a FastAPI service with a React dashboard.

This is a from-scratch rebuild of a university research project on large-scale
traffic prediction (streaming ingestion, data pipelines, and deployed ML
models). All sensor data here is **synthetic but realistic** — rush-hour
patterns, weekday/weekend differences, incidents — generated by the included
simulator, so the whole system runs without any external data feed.

## Architecture

```
┌─────────────┐   stream    ┌────────────┐  batch   ┌──────────┐
│  simulator  │ ──────────▶ │ ingestion  │ ───────▶ │ postgres │
│ (29 sensors │  (Redis     │ (validate, │  insert  │ readings │
│  5 metros)  │   Streams)  │  batch)    │          └────┬─────┘
└─────────────┘             └─────┬──────┘               │
                                 │ cache latest         │ ETL (multi-source:
                                 ▼                      ▼  DB + CSV dumps)
                          ┌────────────┐          ┌──────────────┐   train   ┌───────────┐
                          │   redis    │          │hourly_features│ ───────▶ │  models   │
                          └─────┬──────┘          └──────────────┘           │(XGBoost / │
                                │                                            │ sklearn)  │
┌────────────┐  GET /predict    │                                            └─────┬─────┘
│ dashboard  │ ───────────────▶ │  FastAPI: /sensors, /latest, /history, /predict │
│ (React)    │                  │  (Redis-cached, predictions logged to Postgres)  │
└────────────┘                  └──────────────────────────────────────────────────┘
```

## Components

| Path | What it does |
|---|---|
| `services/simulator` | Generates realistic sensor data (speed/volume/occupancy) for 29 sensors in NYC, LA, Chicago, Houston, Atlanta. Live mode or fast backfill. |
| `services/ingestion` | Consumes the stream, validates with Pydantic, batch-inserts to Postgres (dedupe-safe), refreshes per-sensor latest in Redis. |
| `pipelines/etl` | Multi-source batch ETL: merges the live `readings` table with DOT-style CSV dumps, cleans (nulls, dupes, out-of-range, corrupt rows), aggregates to hourly features. |
| `ml` | Feature engineering (lags, rolling means, calendar features), trains XGBoost vs. sklearn baseline per target, keeps the winner, writes `metrics.json`. |
| `services/api` | FastAPI: sensor catalog, latest readings (cache-first), 24h history, `POST /predict` for next-hour speed/volume + congestion level. |
| `frontend` | React + Vite dashboard: live sensor grid, 24h history chart, next-hour forecast. |
| `infra/k8s` | Kubernetes manifests: Postgres/Redis, autoscaled API (HPA 3–20), ingestion, simulator, nightly retrain CronJob. |

## Quickstart (no infrastructure needed)

The stream bus, cache, and database all have in-memory/SQLite fallbacks, so the
full pipeline runs on a laptop with zero setup:

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# Full pipeline in one process (recommended first run):
DATABASE_URL=sqlite:///traffic.db python scripts/smoke_e2e.py
#   -> backfills 30 days of sensor data, ingests it, runs the ETL,
#      trains the models, and serves a prediction through the API.

# Or step by step (same thing, piece by piece):
python scripts/generate_historical.py --months 3   # DOT-style CSV dumps
python -m pipelines.etl.main --days 90             # clean + aggregate to warehouse
python -m ml.train --days 90                       # train + evaluate models

# Serve predictions:
uvicorn services.api.app:app --port 8000
# POST /predict {"sensor_id": "NYC-001"} -> next-hour forecast
# API docs: http://localhost:8000/docs
```

> Separate long-running processes (simulator → ingestion → API) need a shared
> stream bus — run `docker compose up` below for the real Redis-backed setup.

## With Docker Compose (production-like)

```bash
cp .env.example .env
docker compose up --build            # postgres, redis, simulator, ingestion, api, dashboard
docker compose --profile jobs run historical-data   # CSV dumps
docker compose --profile jobs run etl               # warehouse load
docker compose --profile jobs run train             # model training
```

Dashboard: http://localhost:5173 · API docs: http://localhost:8000/docs

## API

| Method | Endpoint | Description |
|---|---|---|
| GET | `/health` | liveness + whether the model is loaded |
| GET | `/cities` | metros with sensors |
| GET | `/sensors?city=` | sensor catalog |
| GET | `/sensors/{id}/latest` | newest reading (Redis, Postgres fallback) |
| GET | `/sensors/{id}/history?hours=24` | hourly aggregates |
| POST | `/predict` | `{sensor_id, target_time?}` → speed, volume, congestion level |

## ML methodology

For each sensor-hour *h*, the model predicts the **next hour's** average speed
and total volume from features known at the end of *h*: 1h/24h lags, 3h rolling
mean, current occupancy, and calendar features of the target hour (rush-hour
flags, weekday/weekend, month). Chronological train/test split — no shuffling,
no leakage. The trainer fits both XGBoost and a sklearn
HistGradientBoosting baseline and keeps the winner per target.

Measured on 30 days of synthetic data (29 sensors, 4,060 test hours):

| Target | Algorithm | RMSE | MAE | R² | Accuracy |
|---|---|---|---|---|---|
| next-hour speed | sklearn HGB | 3.88 mph | 2.08 mph | 0.78 | **96.6%** within ±5 mph |
| next-hour volume | XGBoost | 142 veh/h | 105 veh/h | 0.97 | **91.0%** within ±15% |

Accuracy here means share of forecasts within tolerance — the project's
>80% bar. These numbers are on synthetic data; the pipeline, evaluation, and
serving code are what transfer to real feeds.

## Notes

- Storage optimization: raw 15-minute readings are rolled up to one hourly row
  per sensor (4x fewer rows) before training; the warehouse table is the only
  thing the model ever scans.
- The stream/cache layers degrade gracefully: `STREAM_BACKEND`/`CACHE_BACKEND`
  fall back to in-memory implementations when Redis is unreachable, which is
  what makes the zero-infra quickstart possible.
- Model artifacts (`ml/artifacts/*.joblib`) are gitignored — train them with
  `python -m ml.train`.
